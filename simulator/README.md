# simulator — 순수 파이썬 로보틱스 시뮬레이터 (URDF + ROS2 노드 구조 흉내)

4륜 베이스 + 매니퓰레이터(4관절+그리퍼) + 그리퍼 장착 RGBD 카메라 + 몸통
3D 라이다를 가진 로봇을, MuJoCo/PyBullet 같은 물리엔진이나 실제 ROS2
없이 **numpy만으로** 시뮬레이션한다. URDF 파싱, 정기구학(FK), 레이캐스팅
기반 센서 시뮬레이션, ROS2 스타일 노드/토픽 구조를 전부 이 저장소
안에서 직접 구현했다.

## 실행

```bash
cd simulator
uv run python run.py                          # 기본(예시) 로봇 + 예시 맵
uv run python run.py --urdf my.urdf --map my_map.json   # 직접 만든 파일로
```

뷰어를 켜면 터미널에도 아래와 같은 사용법이 그대로 출력된다.

## 조작법

| 입력 | 동작 |
|---|---|
| `W` / `S` | 전진 / 후진 (키보드 teleop) |
| `A` / `D` | 좌회전 / 우회전 |
| `Space` | 정지 |
| 맵 패널(왼쪽) 클릭 | 그 좌표로 내비게이션 목표 설정 (`goto`와 동일) |
| 화면 맨 아래 "명령" 입력창 | **먼저 마우스로 클릭해서 커서를 넣어야 타이핑이 먹힌다** (안 그러면 W/S/A/D teleop 키로 먼저 잡아먹힘). 타이핑 후 Enter로 실행 |

**명령 입력창 문법** (전부 소문자, 공백으로 구분):

| 명령 | 문법 | 예시 | 하는 일 |
|---|---|---|---|
| 집기 | `pick <object_id>` | `pick cube_1` | 해당 물체 위로 이동→내려가서 집기→들어올리기 (MoveIt 역할, 아래 참고) |
| 그리퍼 이동 | `move <x> <y> <z>` | `move 0.4 0.0 0.3` | 그리퍼를 그 좌표(map 기준)로 IK로 이동 |
| 놓기 | `place <x> <y> <z>` | `place 0.3 0.1 0.2` | 쥐고 있던 물체를 그 좌표에 놓기 |
| 내비게이션 | `goto <x> <y>` | `goto 2.0 1.5` | 그 좌표까지 A*로 경로 계획 후 자동 주행 (맵 클릭과 동일) |

`object_id`는 맵 JSON 파일의 `objects` 목록에 있는 `id` 값이다 (기본
맵은 빨강 `cube_1`/파랑 `cube_2`/노랑 `cube_3`(테이블 위) + 보라 `ball_1`
(바닥) — 터미널에 뷰어 실행 시 이 목록이 출력된다).

**바로 따라 해볼 수 있는 예시** (실제로 성공하는 것까지 확인한 순서):
```
goto 2.9 -2.0      # 테이블(2.5,-2.0) 근처로 이동할 때까지 기다렸다가
pick cube_1        # 입력 — 벌리기→이동→내려가기→집기→들기까지 자동 진행 (몇 초 걸림)
```
`pick`은 물체까지 팔이 닿는 거리에 있어야 성공한다 — 너무 멀면
"error: target unreachable"이 뜨는데, 그러면 `goto`로 더 가까이 간
다음 다시 `pick`을 입력하면 된다.

## 화면 구성 (각 패널이 보여주는 것)

| 패널(위치) | 보여주는 것 |
|---|---|
| 맵 탑뷰 (왼쪽, 큰 패널) | 회색 도형=고정 장애물, 각 물체 고유색 도형=집을 수 있는 물체, **파란 삼각형**=로봇의 실제 위치(ground truth), **빨강 점선 삼각형**=odom 날것 추정치(보정 전, 계속 드리프트함), **초록 점선 삼각형**=라이다 보정 후 추정치(NavNode가 실제로 쓰는 값), **진한 초록 점**=이번 스캔 순간의 라이다 점(보정된 위치 기준), **옅은 파랑 점**=지금까지 로봇이 돌아다니며 누적해서 파악한 지도(=SLAM이 만들어낸 산출물 — 시간이 지날수록 회색 벽 모양과 겹쳐져야 정상), 보라 점선=내비게이션 경로, 주황 별=내비게이션 목표 |
| RGB (오른쪽 위) | 그리퍼에 달린 카메라가 지금 보는 컬러 화면. 팔이 움직이면 그대로 바뀐다 |
| Depth (오른쪽 위, RGB 옆) | 같은 카메라의 뎁스(거리) 화면 — 밝을수록 가까움 |
| 로봇 현재 형태 (오른쪽 중간, 3D) | URDF 형상을 지금 이 순간의 관절 값 그대로 그린 3D 미리보기 — 팔/그리퍼 자세가 실시간으로 반영됨 |
| 하단 상태 텍스트 | 실제/odom/보정후 위치 좌표와 어긋난 정도(m), 내비게이션·매니퓰레이션 상태, 지금 그리퍼가 쥔 물체 |

## MoveIt(매니퓰레이션)은 있음

`moveit/ik.py`(수치 IK 솔버) + `moveit/arm_node.py`(pick/
place 시퀀스, 위 표의 "매니퓰레이션" 항목)가 MoveIt 역할이다 — `pick`/
`move`/`place` 명령이 전부 이걸 거쳐 실행된다. 다만 실제 MoveIt처럼
장애물을 피해가는 충돌회피 경로계획(RRT 등)은 없고, 그냥 목표 좌표로
직선적으로 IK를 수렴시키는 단순한 버전이다(장애물이 팔 경로 중간에
있어도 피하지 않고 그냥 그 자세로 수렴하려 한다) — "순수 파이썬 +
운동학만" 범위에 맞춘 단순화이고, 필요하면 다음 단계로 확장 가능하다.

## 맵 파일 형식 (사용자가 직접 작성)

`world/map_io.py` 참고. 3D 도형(box/cylinder/sphere)을 나열하는 JSON —
`maps/example_room.json`이 예시다. 라이다/카메라가 3D이므로 2D
점유격자가 아니라 이 방식을 택했다 (자세한 이유는 `world/map_io.py`
상단 주석).

## URDF 파일 (사용자가 직접 작성)

`urdf/parser.py`가 표준 URDF(box/cylinder/sphere 형상, fixed/revolute/
continuous/prismatic 관절)를 직접 파싱한다. `robots/example_robot.urdf`가
이 시뮬레이터가 기대하는 링크 이름(`base_link`, 바퀴 4개, `lidar_link`,
`gripper_base_link`, `camera_link`, 팔 관절들)을 보여주는 예시다 —
직접 만든 URDF를 쓰려면 `run.py`의 `ARM_JOINTS`/`FINGER_JOINTS`와 각
노드가 참조하는 링크 이름을 자기 URDF에 맞게 바꿔주면 된다.

## 메시지 타입 시스템

`msgs.py`에 `geometry_msgs/Twist`, `sensor_msgs/JointState`,
`sensor_msgs/Image`, `nav_msgs/Odometry` 등 실제 ROS2 표준 메시지를
흉내낸 dataclass들이 정의되어 있다. 모든 토픽은 처음 선언될 때(퍼블리셔/
서브스크라이버를 만들 때) 타입이 고정되고, `nodes/core.py`의 `Bus`가
그 뒤로 다른 타입이 발행되면 바로 `TypeError`를 낸다 — 진짜 ROS2가
토픽 타입을 엄격히 강제하는 것과 같은 효과를, DDS 직렬화 없이 파이썬
레벨의 `isinstance` 검사로 흉내낸 것이다. `/joint_states`(여러 관절을
`sensor_msgs/JointState` 하나로 모아 발행 — `nodes/joint_state_aggregator.py`)
가 실제 ROS2 로봇들의 관례를 그대로 따른 대표적인 예다.

## 아키텍처 — 디렉토리가 곧 ROS2 개념

| 디렉토리 | ROS2 개념 | 내용 |
|---|---|---|
| `math3d.py`, `urdf/`, `robot/` | tf2 (좌표계 트리) | URDF 파싱 + 정기구학(FK) + 바퀴 운동학 |
| `world/` | (시뮬레이터 내부) | 맵 로딩 + 레이캐스팅 (라이다/카메라 공통 엔진) |
| `nodes/` | 센서/액추에이터 노드 | 바퀴 4개(각각 노드), 팔 관절마다 노드, 라이다, RGBD 카메라, IMU — 각자 자기 주기(rate_hz)로 동작 |
| `localization/` | **Composable Node** | 여러 센서값을 조합해 위치를 추정하는 노드 — `odom_node.py`(휠 오도메트리), `lidar_localization_node.py`(라이다 스캔매칭 보정) 실제 구현, `slam_stub.py`(비주얼 오도메트리)는 아직 스텁 |
| `nav/` | Nav2 | A* 전역 경로계획 + 목표 추종 로컬 컨트롤러 |
| `moveit/` | MoveIt | 수치 IK 솔버 + pick/place 시퀀스 |
| `viewer.py`, `run.py` | RViz + launch 파일 | GUI + 전체 배선 |

`nodes/core.py`의 `Node`/`ComposableNode`/`Bus`/`Executor`가 이 모든
노드가 공유하는 아주 작은 pub/sub 프레임워크다 (진짜 ROS2처럼
프로세스 분리·DDS는 없고, 한 프로세스 안에서 토픽으로 통신하는
구조만 그대로 흉내냈다).

## 핵심 설계 결정 (지난 대화에서 확정한 것)

- **운동학(Kinematic)만, 실제 동역학 없음**: 중력/마찰/충돌 반작용력을
  계산하지 않는다. 바퀴는 명령 속도대로 굴러가고, 팔은 IK로 계산한
  목표 각도로 이동한다. "순수 파이썬 + 직접 구현" 범위에 맞춘 선택.
- **odom은 일부러 부정확하다**: `localization/odom_node.py`가 바퀴
  반지름을 실제보다 3% 잘못 알고 있다고 가정(+엔코더 노이즈)한 채
  적분한다. 그래서 로봇이 움직일수록 "실제 위치(ground truth)"와
  "odom 날것 추정치"가 서서히(무한정) 벌어진다 — 화면에서 파란
  로봇(실제)과 빨강 점선(odom 날것)이 갈라지는 게 바로 이것이다.
- **`localization/lidar_localization_node.py`가 이 드리프트를 실제로
  보정한다**: 지금 odom이 믿는 위치 근처에서 작은 (dx, dy, dyaw) 후보들을
  여러 개 만들어보고, 그 후보로 라이다 점들을 map 좌표계로 옮겼을 때
  실제 지도의 장애물 칸에 몇 개나 들어맞는지 세서(grid correlation scan
  matching — ICP보다 단순하지만 원리는 같다) 가장 잘 맞는 후보를
  선택하는 방식이다. 화면의 초록 점선(=보정 후 추정치)이 이거고,
  라이다 점(초록)도 이 좌표계 기준으로 그린다. 실측 결과 odom 날것은
  76초 동안 0m→0.9m로 무한정 벌어지는 반면, 보정 후 추정치는 같은
  시간 동안 0.08~0.2m 사이에서 안정적으로 유지됐다 — SLAM/로컬라이제이션이
  실제로 해야 하는 일(드리프트를 무한정 쌓이지 않게 계속 깎아내는 것)을
  확인했다.
  ⚠️ 구현 시 실수했던 부분: 처음엔 Nav용 `OccupancyGrid`(경로계획 안전
  마진 0.35m가 덧씌워진 "부풀린" 격자)를 그대로 재사용했는데, 그러면
  아무 위치나 "적중"으로 잘못 판정돼서 오히려 보정이 위치를 더 틀어지게
  만들었다. 스캔 매칭에는 실제 벽 크기 그대로의(안전마진 없는) 별도
  격자가 필요하다.
- 카메라(뎁스+RGB) 기반 비주얼 오도메트리는 아직 스텁이다
  (`localization/slam_stub.py`) — 이유는 그 파일 상단 주석 참고
  (그리퍼에 달려 팔이 움직이면 시야가 같이 바뀌는 데다 시야각도 좁아서,
  360도 몸통 고정인 라이다보다 로컬라이제이션 소스로 쓰기 어렵다).
- **Nav2 역할의 `NavNode`는 ground truth가 아니라 위 라이다 보정이
  적용된 추정치(`corrected_pose`)를 보고 움직인다** (실제 Nav2도 순수
  odom이 아니라 amcl 등 로컬라이제이션 결과를 쓴다) — 그래도 그 추정이
  100% 정확하진 않으므로, 목표에 "도착했다"고 판단하는 시점과 실제로
  도착한 위치가 미세하게 다를 수 있다.

## 아직 안 만든 것 (다음 단계)

- `localization/slam_stub.py`: 카메라(뎁스+RGB) 기반 비주얼 오도메트리.
- 실제 파지 물리(마찰/접촉력)는 없음 — "잡음"은 운동학적으로
  그리퍼 위치를 물체 위치에 그대로 동기화하는 방식으로 흉내냈다.

## 고쳤던 버그들 (기록)

- **팔이 순간이동하던 문제**: IK가 `robot.joint_positions`를 직접
  수렴시키는 알고리즘이라, 계산이 끝나는 순간 이미 최종 자세가 화면에
  보여버렸다. IK 계산 후 관절값을 원래대로 복구하고, 계산해낸 목표값만
  JointNode에 "발행"해서 실제 움직임은 JointNode의 속도 제한 보간이
  담당하게 고쳤다 (`moveit/arm_node.py`의 `_move_to`). 또한 pick 같은
  다단계 시퀀스가 각 단계의 "도착"을 기다리지 않고 매 틱 바로 다음
  단계로 넘어가던 것도, 목표에 충분히 가까워질 때까지 기다렸다가
  넘어가도록 고쳤다(`_arrived()`).
- **그리퍼 손가락이 전혀 안 움직이던 문제**: `ArmNode`가 손가락 명령을
  발행할 때 관절 이름(`left_finger_joint`)을 그대로 토픽 이름으로
  썼는데, `JointNode`는 짧은 토픽 이름(`left_finger`)으로 구독하고
  있어서 서로 다른 토픽이 되어 명령이 전달되지 않고 있었다. 팔 관절과
  마찬가지로 `joint_name -> topic_name` 매핑을 제대로 전달하도록
  고쳤다. (이 버그는 원래부터 있었는데, "도착까지 기다리기" 로직을
  넣고 나서야 — 손가락이 영원히 목표에 안 닿으니 — 드러났다.)
- **테이블 위 물체를 아무리 가까이 가도 못 집던 문제**: 원인이 3중으로
  겹쳐 있었다.
  1) 테이블이 너무 크고 높아서(원래 0.8x0.5x0.7), Nav 안전마진(당시
     0.35)까지 더하면 로봇이 절대 팔이 닿는 거리까지 못 붙었다 — 테이블을
     작고 낮게(0.3x0.3x0.35) 줄이고, Nav 안전마진도 로봇 몸체 크기에
     맞게 0.35→0.15로 줄였다.
  2) 그래도 실제 도착 지점이 기대보다 최대 0.2m 이상 더 멀었다 —
     `goal_tolerance`가 너무 넉넉했고(0.25→0.12로 축소), 로컬라이제이션
     보정이 로봇이 멈춰있을 때도 계속 재탐색하며 추정 위치를 미세하게
     흔들고 있었다(바퀴가 실제로 돌고 있을 때만 보정하도록 고침,
     `odom_node.is_moving`).
  3) 그래도 가끔 "분명 닿는 거리인데" 실패하는 경우가 남아있었는데,
     알고 보니 IK가 국소최적점(local minimum)에 갇히는 문제였다 — 로봇
     몸체가 바라보는 방향과 크게 어긋난 목표는 관절을 크게 돌려야
     하는데, 그 경로 중간에 수렴이 막히는 경우가 있었다. 첫 시도가
     실패하면 관절 한계 범위 안에서 무작위 시작 자세로 몇 번 재시도하는
     멀티스타트(multi-start)를 추가해서 해결했다(`moveit/ik.py`).
  여기에 더해 팔 자체의 물리적 도달거리도 넉넉하게 늘렸다(피벗 기준
  최대 수평 도달거리 약 0.47m → 0.9m 이상).
- **팔꿈치가 반대로 꺾인 것처럼 보이던 문제**: `elbow_pitch_joint`의
  회전 범위가 `-2.6~2.6`로 양쪽 다 열려있었다. 이 팔은 목표 하나에
  도달하는 관절 조합이 여러 개 있을 수 있는 구조라(관절 4개로 3차원
  좌표 하나를 맞추는 문제라 여유 자유도가 1개 있음), IK가 수학적으로는
  맞지만 사람 팔꿈치처럼 자연스럽게 굽는 게 아니라 반대 방향으로 꺾인
  해를 고를 수 있었다. 실제 팔꿈치처럼 한쪽으로만(`0~2.6`) 굽도록
  제한해서, 항상 일관되고 자연스러운 방향으로만 굽게 고쳤다.
