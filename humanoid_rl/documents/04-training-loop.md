# 04. 학습 루프와 실행 방법

관련 코드: `train.py`, `rl/vec_env.py`, `play.py`

## 벡터 환경(Vectorized Environment)

`rl/vec_env.py`의 `SyncVectorBipedEnv`는 `BipedEnv` 인스턴스 N개(기본
8개)를 리스트로 들고, 매 스텝 N개 모두에게 각자의 행동을 적용합니다.

중요한 디테일: 한 환경이 넘어지거나 시간초과로 끝나면, **그 환경만** 즉시
`reset()`해서 다음 에피소드를 바로 이어갑니다. 나머지 N-1개가 끝날 때까지
기다리지 않습니다 — 이렇게 해야 8개 환경이 항상 쉬지 않고 데이터를
생산하고, 서로 다른 시점에 서로 다른 상황(하나는 막 시작, 다른 하나는
목표 근처)을 겪게 되어 한 번의 업데이트에 훨씬 다양한 경험이 섞입니다.

### 멀티코어 병렬 실행 (`--multiprocess`)

`SyncVectorBipedEnv`는 N개 환경을 파이썬 for문으로 "순서대로" 진행시킨다
— 코드는 단순하지만 파이썬의 GIL(Global Interpreter Lock) 때문에 이
방식으로는 CPU 코어 하나만 실제로 쓰이고, 나머지 코어는 놀게 된다.

`rl/subproc_vec_env.py`의 `SubprocVectorBipedEnv`는 환경 하나마다 완전히
별도의 OS 프로세스를 띄운다. 프로세스는 GIL의 제약을 받지 않으므로
운영체제가 각각을 서로 다른 CPU 코어에 진짜로 동시에 배정한다. 직접
측정 결과 8개 환경 기준 환경 스텝 처리량이 약 2.3배 빨라졌다(순수 환경
스텝 기준, 신경망 연산 제외).

```bash
uv run python train.py --multiprocess
```

**`--watch`와는 함께 쓸 수 없다.** 각 환경이 서로 다른(별도) 프로세스에
있어서, 메인 프로세스가 그 환경의 `model`/`data`를 직접 들여다보며
화면을 그릴 방법이 없기 때문이다(파이프로 그림 데이터를 통째로
주고받는 방법도 있겠지만 지금은 구현하지 않았다). 시각화가 필요하면
`--watch`만, 최고 속도가 필요하면 `--multiprocess`만 쓸 것.

### 파이프라이닝 (`--pipeline`) — 학습 중 워커가 노는 시간 없애기

실측해보면(위 `--multiprocess` 섹션과 별개로) 한 이터레이션의 시간 대부분이
"PPO 업데이트"(신경망 학습) 한 단계에 몰려 있고, 그동안 환경(워커)들은
할 일이 없어 완전히 놀게 된다 — 예를 들어 1.58초짜리 이터레이션 중
업데이트가 1.07초(68%)를 차지하면, 워커들은 그 68% 동안 CPU를 전혀
쓰지 않는다. `--multiprocess`로 아무리 워커를 늘려도 이 구조적인
유휴 시간은 줄지 않는다.

`--pipeline`은 "다음 롤아웃 수집"과 "지금 데이터로 학습"을 서로 다른
스레드에서 동시에 진행해서 이 유휴 시간을 없앤다.

```bash
uv run python train.py --multiprocess --pipeline
```

직접 측정 결과(8워커, 11초 동안): `--multiprocess`만 썼을 때 14
이터레이션 진행된 것이, `--pipeline`을 더하면 22 이터레이션으로
**약 1.57배** 빨라졌고, 워커별 CPU 사용률도 14~15%에서 22~26%로
확실히 올랐다.

**추가로: `--train_epochs`/`--minibatch_size` 기본값 조정.** 업데이트
자체가 롤아웃보다 훨씬 오래 걸리는 게 겹침 효율의 한계였기 때문에,
업데이트를 더 짧게 만들면(적은 epoch, 큰 미니배치) 겹치는 비율이
올라간다. 그래서 기본값을 `train_epochs=10→4`, `minibatch_size=256→512`로
낮춰뒀다. 스테디스테이트 구간에서 직접 비교한 결과 초당 이터레이션이
2.33 → 2.8(**약 20% 추가 향상**)로 늘었다. 다만 이게 "공짜"는 아니다 —
같은 데이터를 재사용하는 횟수(epoch)가 줄어드는 만큼 한 번 모은
데이터에서 뽑아내는 학습 신호의 양도 줄어, 최종 정책 품질/수렴 속도에
약간의 트레이드오프가 있을 수 있다. 예전 설정(`--train_epochs 10
--minibatch_size 256`)으로 되돌리고 싶다면 그냥 그 값들을 다시 지정하면 된다.

**여기가 사실상의 실질적 한계다.** CPU 사용률을 20~30%대에서 훨씬 더
끌어올리려면(예: 80~100%), 지금처럼 워커가 매 스텝 메인 프로세스에게
"다음에 뭘 할지" 물어보고 기다리는 구조 자체를 바꿔야 한다 — 각 워커
프로세스 안에 정책 신경망 사본을 두고 스스로 행동을 결정하게 해서
왕복 지연 자체를 없애는 방식이다. 이건 각 워커에 TensorFlow를 새로
띄우고 가중치 동기화 메커니즘을 만들어야 하는 훨씬 큰 재설계라, 이
프로젝트 규모(작은 모델, 노트북 학습)에서는 투자 대비 효과가 크지
않다고 판단해 지금은 적용하지 않았다.

**어떻게 안전하게 동시에 돌리는가**: 두 스레드가 신경망의 "같은" 가중치를
동시에 읽고 쓰면(하나는 추론, 하나는 경사하강 업데이트) 애매하게 절반만
갱신된 가중치를 읽어버리는 경쟁 상태(race condition)가 생길 수 있다.
이를 피하기 위해 `rl/ppo.py`의 `PPO`는 학습되는 진짜 네트워크(`ac`)와
롤아웃 수집 전용으로 "얼려둔" 사본(`ac_infer`)을 따로 둔다. 롤아웃
스레드는 `ac_infer`만 읽고, 학습 스레드는 `ac`만 갱신하므로 절대 같은
메모리를 동시에 건드리지 않는다. 두 스레드가 모두 끝난 안전한
시점(이터레이션 경계)에만 `agent.sync_infer()`로 최신 가중치를
`ac_infer`에 복사한다.

**부작용(트레이드오프)**: 이 구조상 롤아웃은 항상 "한 이터레이션만큼
살짝 뒤처진(stale)" 정책으로 수집된다 — 지금 막 업데이트를 마친
최신 정책이 아니라, 그 이전 정책으로 다음 데이터를 모으기 시작했기
때문이다. PPO는 원래도 여러 epoch 동안 정책이 조금씩 바뀌는 것을
clip으로 허용하는 알고리즘이라 이 정도 지연은 대체로 무시할 만한
수준이지만, 학습이 불안정해 보인다면 `--pipeline`을 빼고 비교해볼 것.

**`--watch`와는 함께 쓸 수 없다** — 화면 그리기(OpenCV)는 메인
스레드에서만 안전하게 할 수 있는데, `--pipeline`은 롤아웃 수집을
백그라운드 스레드로 옮기기 때문이다.

### GPU(Metal) 사용 안 함

이 프로젝트는 CPU로만 학습한다. Apple Silicon의 GPU 가속(`tensorflow-metal`)을
설치해봤지만, 이 환경의 `uv` 파이썬 배포판과 라이브러리 경로가 맞지
않아(`Library not loaded: @rpath/_pywrap_tensorflow_internal.so`) 설치가
깨지는 문제가 있어 제거했다. 다만 이 프로젝트 규모(작은 신경망 + MuJoCo
물리 연산이 병목)에서는 GPU가 있어도 큰 이득이 크지 않을 가능성이 높다
— 신경망이 아주 작아서 GPU로 보내는 오버헤드가 계산량보다 커질 수 있고,
진짜 병목은 물리 시뮬레이션(CPU 연산)이기 때문이다. 그래서 `--multiprocess`로
CPU 코어를 더 쓰는 쪽이 실질적으로 더 효과적이다.

## train.py의 한 이터레이션

```
1. 롤아웃 수집: n_steps(256)만큼 N(8)개 환경을 동시에 진행
   -> 총 256*8 = 2048개의 (상태, 행동, 보상, ...) 수집
2. GAE로 advantage/return 계산
3. (T,N,...) 형태를 (T*N,...)로 펼쳐서 PPO 업데이트 (10 epoch)
4. 로그 출력, 필요하면 체크포인트 저장
```

```
n_iters = total_timesteps / (n_envs * n_steps)
```

기본값(`total_timesteps=2,000,000`, `n_envs=8`, `n_steps=256`)이면
약 976번의 이터레이션이 돕니다.

## 실행 방법

```bash
# 학습 시작 (기본 200만 스텝, PC 성능에 따라 다르지만 대략 30분~1시간대)
# map_path/scenario를 안 주면 기본적으로 매 에피소드 무작위 맵으로 학습된다
# (이유는 06-map-files.md 참고 — 특정 맵 하나만 외우는 것을 피하기 위함)
uv run python train.py

# 더 짧게 맛보기
uv run python train.py --total_timesteps 200000

# 환경 개수/스텝 수 등 조절
uv run python train.py --n_envs 16 --n_steps 512

# 학습된 정책을 실제로 눈으로 보기 (MuJoCo 3D 뷰어 창이 뜸)
uv run mjpython play.py

# 학습 때 보지 못한 다른 맵/목표로 실제 일반화가 되는지 확인
uv run mjpython play.py --map_path maps/map_default.xml --goal 5.0 -1.0
uv run mjpython play.py --randomize_map   # 매 에피소드 새 무작위 맵으로 테스트
```

체크포인트는 `checkpoints/{ckpt_name}_actor.weights.h5`,
`checkpoints/{ckpt_name}_critic.weights.h5`, `..._log_std.npy` 세 파일로
저장되며, `play.py`가 이 세 가지를 함께 불러와 정책을 복원합니다.

## 학습 로그 읽는 법 (실전)

아래는 이 프로젝트를 실제로 처음 돌렸을 때 나온 초반 로그의 흐름입니다.

```
iter 1   ep_return -6.6   ep_len 28   entropy 7.38
iter 20  ep_return  4.8   ep_len 52   entropy 7.63
iter 58  ep_return 25.8   ep_len 113  entropy 7.85
```

- **ep_return이 우상향**: 좋은 신호. 정책이 뭔가 유용한 걸 배우고 있다는 뜻.
- **ep_len이 함께 늘어남**: 특히 초반에는 "목표에 도달해서" 에피소드가
  끝나는 게 아니라 "안 넘어지고 오래 버텨서" 자연스럽게 길어지는 것.
  이는 강화학습이 문제를 푸는 순서상 매우 정상적인 패턴입니다 —
  "일단 서 있기"를 먼저 배우고, 그 다음에야 "이동하기"를 배우기 시작합니다.
- **entropy는 보통 서서히 감소해야 하는데, 초반에 오히려 증가하기도
  합니다.** 아직 뚜렷하게 좋은 행동을 찾지 못한 시기에는 엔트로피
  보너스(탐험 장려)가 우세해 정책이 오히려 더 무작위로 움직이려는
  경향을 보일 수 있습니다. 학습이 진행되며 "이 방향이 확실히 낫다"는
  신호가 쌓이면 자연스럽게 감소세로 돌아서는 경우가 많습니다. 수십만
  스텝이 지나도 계속 증가하기만 한다면 `ent_coef`를 낮추는 것을
  고려해볼 수 있습니다 (`rl/ppo.py`의 `PPO.__init__` 인자).
- **success(목표 도달 비율)는 한동안 0에 머무를 수 있습니다.** "쓰러지지
  않고 버티는 것"과 "실제로 3~6m 떨어진 목표까지 이동하는 것" 사이에는
  꽤 큰 난이도 차이가 있어서, ep_len이 충분히 길어진 뒤에야 서서히
  오르기 시작하는 것이 일반적입니다.

## 문제가 생겼을 때 체크리스트

- **ep_return이 계속 바닥을 기고 ep_len도 안 늘어남**: 학습률(`--lr`)을
  낮춰보거나(`1e-4`), `n_steps`/`n_envs`를 늘려 한 번의 업데이트에 더
  많은 데이터를 모아보세요.
- **value_loss가 계속 매우 크거나 발산함**: advantage 정규화는 이미
  되어 있으므로, 보상 스케일 자체가 너무 크지 않은지 확인
  (`envs/biped_env.py`의 `_compute_reward` 계수들).
- **entropy가 0으로 급격히 붕괴함(조기 수렴)**: `ent_coef`를 높여보세요
  (기본 0.01 → 0.02~0.05).
- **kl(approx_kl)이 자주 0.1을 넘음**: 한 번의 업데이트가 너무 급격하다는
  뜻. 학습률을 낮추거나 `train_epochs`를 줄이세요.

더 근본적인 개선 방향(더 오래/더 많은 환경으로 학습, 커리큘럼 학습,
관찰값 정규화 등)은 [05-next-steps.md](05-next-steps.md)에 정리했습니다.
